# Party Master (frmPartyMaster.frm) Analysis

## 1. UI Components & Structure
The Party Master is a complex multi-tab form used for creating and managing Vendors, Customers, and Parties.
- **Main Header**:
  - `cmbAcType`: Creditor, Debtor, Party.
  - `tbPartyName`: Account Name.
  - `txtVendorCode`: Auto-generated code (e.g., `Vxxx001` or `Cxxx001`).
  - `cmbStatus`: Active / InActive.
- **Address Tab**:
  - Contains fields for Address (3 lines), Country, State, City, PIN, Phone, Fax, Cell, Email.
  - Registration fields: LST No/Date, CST No/Date, Supplier Code.
  - Udyam Registration fields (Type, No, Date).
- **Details Tab**:
  - PAN, TIN, ECC No, Range, Area Code, Contact Person, Subcontractor checkbox.
- **GST Tab**:
  - Provisional ID, GST Reg No, GST Reg Date.
- **Terms Tab**:
  - Lookups for Form, Packing & Forwarding, Delivery, Insurance, Freight, Mode, Payment Terms (all sourced from `TERMSMASTER`).
  - Dropdowns for Customer Formula and Vendor Formula (sourced from `COM_FormulaMast_Hdr`).
  - Dropdown for Currency (sourced from `COM_Currency_Master`).
  - Dropdown for Credit Days Period (Delivery, Last Receipt, Last RR Approval, Invoice).

## 2. Business Rules & Logic
- **Validation**: Strict validation across tabs (e.g., if Address 1 is entered, City must be entered). Dates cannot be greater than Current Date. Formulas must be selected based on Account Type (Debtor requires Customer Formula, Creditor requires Vendor Formula).
- **Code Generation**: `txtVendorCode` is auto-generated by querying `Max(VendorCode)` from `FAS_PARTY_MASTER` grouping by `AcType` ('P', 'D', 'C') and the first letter of the PartyName.
- **FAS Sync**: Party Master is tightly coupled with the accounting module. It explicitly checks `FAS_LedgerMaster` to see if a ledger exists. 

## 3. Database Interactions (Dependencies)
The form interacts with the following tables and stored procedures:
- **Main Save Targets**:
  - `FAS_LedgerMaster` (via `FAS_Ins_LedgerMaster` and `FAS_UP_LedgerMaster`)
  - `FAS_PARTY_MASTER` (via `FAS_INS_PARTY_MASTER` and `FAS_UP_PARTY_MASTER`)
  - `FAS_PARTY_ADDRESS` (via `FAS_INS_PARTY_ADDRESS` and `FAS_UP_PARTY_ADDRESS`)
- **Dropdown Dependencies (Sub-Masters)**:
  - **City/State/Country**: Invokes `FAS_PartyMaster_Hlp_City`, `_State`, `_Country`.
  - **Formulas**: Queries `COM_FormulaMast_Hdr`.
  - **Terms**: Queries `TERMSMASTER` based on `TypeFlg` (Form, Packing, Delivery, etc.).
  - **Currency**: Queries `COM_Currency_Master`.

## 4. Potential Migration Risks
- **Massive Scope**: Trying to build all APIs and the multi-tab UI at once will result in context loss and bugs. We MUST phase the implementation.
- **Missing Legacy APIs**: Many sub-masters (Currencies, Formulas) have empty folders in `src/app/api/sales/masters/party` and need their endpoints created before the UI can be built.
- **Stored Procedure Reliability**: As with `DocumentTypeMaster`, we must test if the `FAS_INS_PARTY_MASTER` and `FAS_Ins_LedgerMaster` SPs throw transaction boundary errors (`3902`) in Prisma. If they do, we will need to rewrite the insert logic using Prisma ORM.
- **Auto Code Concurrency**: Generating `Vxxx001` based on the max existing code needs to be handled transactionally to prevent duplicates if two users create a party simultaneously.
